# Observer & PLL — Improvement To-Do List

Source: `docs/Observer_PLL_Explained.html`, section 8 ("How to improve performance further"), written after the missing-saturation fix stopped the sensorless-handoff runaway. Ranked by what the captured plots actually point to.

- [x] **1. Retune so the Bemf estimate settles *below* the clamp, not against it.** — *Done, evolved into a different fix than originally scoped.*
  The estimated back-EMF magnitude sits pinned at the clamp ceiling (~12.7V) for almost the entire run, while the true back-EMF at ~2300 RPM should be ~3.2V. The clamp (`±1.2×p.PLL_BemfPeak_V`) is deliberately generous — the real fix is in the gains that let the correction loop overshoot that far in the first place.
  - Try re-deriving `p.STO_G2`'s pole-placement target eigenvalue with a bit more margin (currently split evenly for critical damping + fastest convergence).
  - Re-examine `pll_wn` (currently 30 Hz) together with `p.PLL_BemfPeak_V` as a pair — change one at a time so effects can be told apart. (Tuning history already in `ss_params.m` comments: 100 Hz picked up PWM/reconstruction ripple, 15 Hz didn't converge inside the ramp window, 30 Hz was the prior compromise — worth revisiting now that the clamp exists as a backstop.)
  - **What actually worked:** re-deriving `p.STO_G2`'s target eigenvalue alone (a slower, less-evenly-split choice, "Step 2a") gave virtually no change in steady-state Bemf magnitude bias (5.66V vs. baseline 5.73V, despite a 53% larger `G2`) — expected in hindsight, see the G1/G2 explanation added to section 9 below: with `G1` fixed, the eigenvalue *sum* is fixed, so `G2` can only redistribute between two poles, not change the observer's achievable bandwidth. The fix that actually worked was replacing the fixed `±1.2×p.PLL_BemfPeak_V` clamp with a **dynamic, Ke-based clamp**: `bemfClampBound = max(Ke·|we_est|·2.5, bemfFloorV)`, where `Ke` is this motor's own measured back-EMF constant (`≈0.00439` V per rad/s electrical, derived from `X5550backEMF_4000rpm.m`'s measured peak at 4000 RPM). This is a deliberate departure from ST, which uses a static worst-case clamp (`MAX_BEMF_VOLTAGE`, not speed-scaled) — the dynamic version tracks the true physical ceiling more tightly, at the cost of the clamp itself becoming self-referential during the handover transient (it collapsed to 0 once with a missing floor — fixed by adding `bemfFloorV`).

- [x] **2. Add ST's convergence gate instead of a fixed-time handoff schedule.** — *Done, with one known simplification vs. ST.*
  ST's firmware hands off based on `STO_PLL_IsObserverConverged()` (estimate within tolerance of forced speed, debounced over consecutive samples), with a fixed-time schedule kept only as a timeout fallback. This model currently hands off purely on `p.Startup_T(end)`, regardless of observer state.
  - Reuse/adapt the `check_convergence()` block already added (compares `we_est` vs `we_target`, `tolFrac` tunable, outputs `isConverged`) and wire it into the angle-blend's trigger in place of the raw constant.
  - **What was built:** a new `handover_timing_gate` MATLAB Function block (inside `Startup`) replaces `angle blend`'s fixed `T5` input with a computed `T5_eff` — latched to the instant 20 consecutive samples fall within `tolFrac` (5%) of `we_target`, with a fixed-time timeout fallback (`T5_fixed + timeoutMargin`) if convergence never happens. Two bugs found and fixed along the way: (a) the timeout branch originally output `t_elapsed` itself (a moving target chasing `angle blend`'s own `t_elapsed >= T5` check, so it could never actually trigger) — fixed by latching to the fixed value `T5_fixed + timeoutMargin` instead, same as the convergence latch; (b) the minimum-speed input (`minSpeed`, see item 3) was first wired as a raw RPM number against a signal that's actually in rad/s electrical — compared to `p.MinStartUpValidSpeed` (already correctly computed in `ss_params.m`) for the fix.
  - **ST comparison, flagged for a decision:** ST's actual `STO_PLL_IsObserverConverged` requires an estimate within a **15%** band (`p.ConvergenceBand_Frac` — already sitting in `ss_params.m`, matching ST's `SPEED_BAND_LOWER_LIMIT`) for **2** consecutive samples (`p.ConvergenceConsecutiveSamples`, matching `NB_CONSECUTIVE_TESTS`), evaluated against ST's own buffered/averaged speed. `handover_timing_gate` currently uses its own harder-coded `tolFrac=0.05` (5%) and `DEBOUNCE_N=20` instead of these two existing, ST-matched constants. Also, ST gates consistency-counting behind a *separate* variance/"is the estimate even reliable" check before applying the tolerance band at all — this gate folds that into just using the filtered estimate directly, a simplification, not an exact match.

- [x] **3. Add ST's `OBS_MINIMUM_SPEED_RPM` equivalent.** — *Done.*
  ST never trusts the observer below 2400 RPM (mechanical) — back-EMF is too small to estimate reliably under that. No equivalent floor exists here yet.
  - **What was built:** `p.MinStartUpValidSpeed` (already defined in `ss_params.m`, `OBS_MINIMUM_SPEED_RPM=2300` → rad/s electrical) now gates `handover_timing_gate`'s consistency counter directly (`abs(we_est) > minSpeed`, alongside the existing time and tolerance conditions) — same role as ST's `MinStartUpValidSpeed` check in `STO_PLL_IsObserverConverged`.

- [ ] **4. Re-examine the 16 kHz (ST) vs. 12.5 kHz (this model) difference.**
  Not the dominant cause of the original runaway (oversampling margin vs. the 30 Hz PLL bandwidth is ~400×, plenty), but a slower control rate leaves less room to hide any residual gain mismatch. Revisit if tuning margin still feels tight after items 1-3.

- [ ] **5. Decouple the G1/G2 pole-placement design from the alpha/beta rotation coupling.**
  `p.STO_G2`'s derivation currently treats alpha/beta as independent single-axis loops for gain *selection*, even though the runtime equations keep the full rotation coupling. A design that accounts for the coupling directly (Bemf_alpha/Bemf_beta as one rotating state, not two decoupled real ones) would likely give a tighter, more accurate gain — relevant now that the goal is clean convergence, not just staying bounded.

- [ ] **6. (New) Decide how to treat the non-sinusoidal back-EMF mismatch.**
  The plant (`FOC_ctrl/BLDC Motor`, `MaskType: BLDC`) uses this motor's actual measured back-EMF profile (`X5550backEMF_4000rpm.m`), which is **not sinusoidal** — the raw data shows a flat-topped, faintly double-humped peak, not a smooth sine crest. The STO's internal model is a pure rotation (can only produce a perfect sinusoid on its own); the G1/G2 correction terms visibly "drag" `Bemf_alpha_est`/`Bemf_beta_est` into the same flat-topped, double-humped shape to track the real signal, and the phase detector (built assuming a clean sinusoidal relationship between Bemf and θ) picks up a matching periodic ripple that shows up directly in `we_est` — synchronized with the electrical cycle, not random noise.
  - This is **not a bug or a tuning gap** — it's a structural mismatch between a sinusoidal-back-EMF algorithm (ST's STO-PLL, designed for PMSM) and a genuinely trapezoidal-back-EMF machine model. ST's own firmware would hit the same issue on this motor.
  - Worth checking: is the real target hardware actually this trapezoidal, or is the Simscape BLDC block/measured profile more aggressive than the real motor's actual shape? If the real motor is closer to sinusoidal, the ripple seen in simulation may be overstated relative to reality.
  - Not chasing this via G1/G2/PLL retuning further — see the G1/G2/Kp/Ki explanation in `Observer_PLL_Explained.html` section 9 for why that lever has limited reach here.
